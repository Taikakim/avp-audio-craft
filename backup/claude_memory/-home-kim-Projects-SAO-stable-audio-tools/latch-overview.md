**LatCH (Latent-Control Heads):** lightweight (~5–7M param) bidirectional transformer heads that predict MIR time-series features from noisy VAE latents, used to apply Training-Free Guidance (TFG) during Stable Audio Open inference. Paper: see [[latch-paper]].

## Code layout
- Head architecture: `stable_audio_tools/models/latch.py` (tracked) and `scripts/latch_model.py` (BiTransformer, RoPE).
- Dataset: `scripts/latch_dataset.py` — maps `/run/media/kim/Lehto/latents` .npy → MIR time-series from `timeseries.db`. Features are pre-resampled to 256 frames (verified: target↔latent frame alignment is correct, no time-warp).
- Training: `scripts/train_latch.py`. Inference: `stable_audio_tools/inference/sampling.py` (`sample_euler_latch_guided`) + `generation.py` (`latch_configs`, `latch_hparams`). UI in `interface/interfaces/diffusion_cond.py`.
- Target builders: `stable_audio_tools/inference/latch_targets.py` (constant/ramp_up/ramp_down/beat_grid).
- Checkpoint v2 format: dict with `state_dict`, `feature_name`, `feature_stats`, `target_kind_default`, `noise_schedule`, `loss_type`.

## The bug-fix chain (2026-05-25) — why "LatCH did nothing" before
The original (Antigravity-written) code had several train/inference inconsistencies. Fixed:
1. **Schedule mismatch (training):** head was forward-noised with VP cosine, but the Small model is `rectified_flow` (linear). `train_latch.py` now takes `--objective` and noises to match (default `rectified_flow`). **A LatCH head MUST be trained with the schedule of the model it will guide.**
2. **Wrong timestep at inference (variance guidance):** the head was queried at a linear step fraction `(num_steps-i)/num_steps`, but the RF sigmoid schedule is nonlinear — see [[latch-sigmas-schedule]]. Now queried at the actual `t_curr`.
3. **Loss mismatch:** sampler used MSE for all heads; beat/onset trained with BCE-logits, hpcp with cosine. Now per-head criterion from `loss_type` metadata.
4. **γ noise augmentation** was added to the head's *output* (and scaled to ~0 by `s_t`); now perturbs the *input* estimate (TFG-style). See [[latch-paper]].
- Plus: warning when a head's `noise_schedule` ≠ the model objective.

## Current state (2026-05-25)
- `rms_energy_bass` head trained 10 epochs (RF schedule). **ep10 verified CONTROLLING bass RMS: correlation(requested, measured)=1.000, monotonic.** See [[latch-verification]]. This validated the whole fix chain end-to-end.
- Old heads (`latch_tonic_ep10.pt`, `latch_spectral_flatness_ts_ep10.pt`) are VP-trained → wrong for the RF model; retrain with `--objective rectified_flow`.
- Big loss numbers in rms training are expected: MSE on dB targets (range −97..−4) skewed by near-silent crops; typical batch loss ~24 (≈5 dB RMS error) means it's learning.

## Controllability map (v2 heads, RF schedule; screened with latch_head_sensitivity.py + probed with latch_probe_encodability.py)
- **STRONG heads (trained + pushed to avp/main, sensitivity OK):** `rms_energy_{bass,body,mid,air}`, `spectral_flux` (sens ~7.8), `spectral_kurtosis`.
- **`beat_activations` — NOT A USABLE CONTROL (verified 2026-05-26, `latch_verify_rhythm.py` + waveform-diff analysis, 5 BPM-free prompts × 3 seeds).** Guidance moves the audio only **dL2 0.06–0.19 vs a seed-scale of 1.48** (~5–13%) — the seed writes the track, guidance is a faint nudge → outputs sound near-identical (user confirmed by ear). **Target is ignored:** g90↔g150 (opposite tempo targets) diverge *as little as* base↔g90 — no "toward 90 vs 150" direction. The earlier "detected BPM 150→111" table was **librosa octave/tracker NOISE on near-identical audio** (same seed reads identical BPM across base/g90/g150), NOT real tempo change. Only real signal: a small dose-dependent perturbation (weight 15/30/50 → dL2 0.051/0.079/0.115). **Drop it from the slider lineup.** Precise **tempo** → native `bpm` conditioner (probe R²≈0.53), not this head; `downbeat`/`onsets` likely the same. **LESSON: trust closed-loop WAVEFORM diff + ears over a beat-tracker's BPM readout** — the tracker hallucinates shifts on audio that barely changed. (VRAM: Stable Audio half = 1.0 GB; analysis is CPU → no contention.)
- **Continuous "rhythmic density" feature — PROMISING (probed 2026-05-26, `latch_prototype_beat_density.py`, 800 crops).** Gaussian-smoothing the sparse binary marker trains into a continuous envelope multiplies linear frame-wise decodability: raw `beat_activations` R²≈0.03 (≈none — *this* is why the head was dead, the spikes aren't decodable) → σ=3/ctx±4 R²≈0.14–0.20. **`onsets_activations` smooths far better: raw ~0.10–0.16 → σ=3 R²≈0.33–0.34 (moderate).** So a smoothed **onset-density** head is the viable continuous rhythmic control — "how busy/active," decoupled from tempo (tempo→bpm conditioner). Linear R² is a LOWER bound (the BiTransformer head should exceed it, as rms did at comparable probe R²). Sweet spot σ≈3 frames (~140ms); ctx±4 > ctx±0. **IMPLEMENTED (2026-05-26):** on-the-fly smoothing in `LatCHDataset` (`smooth_kind` ∈ none/gaussian/linear/lowpass/beat_weighted, `smooth_width` in frames) + deterministic `subset_frac`/`subset_seed`; `train_latch.py` exposes `--smooth-kind/--smooth-width/--subset-frac/--subset-seed`, routes smoothed marker features to regression (SmoothL1, not BCE), defaults target kind to `constant`, stores smoothing in ckpt metadata. `beat_weighted` boosts on-beat onsets via the beat grid (a "pulse clarity" target vs plain "density"). Bake-off config: `latch_train_density.yaml` (4 ep / 30% data / `--standardize` so val-loss is comparable ACROSS kinds). **BAKE-OFF DONE (2026-05-26):** `gaussian` σ3 WINS (val_median 0.191) > `linear` 0.225 > `lowpass` 0.238 > `beat_weighted` 0.252 — the on-beat-weighted variant was the WORST (weighting on-beat onsets made the target *harder* to predict; drop that idea). Use plain gaussian. GUI hyperparam maxima 10×'d (ρ/μ→300, γ→20, iters→80, Weight→500).
- **madmom soft probabilities (decided 2026-05-26, from the MIR-side instance):** when the dataset is re-analysed, use madmom's NATIVE per-frame soft beat/downbeat/onset *probabilities* directly — they're already the continuous dense envelope the gaussian-smoothing was reconstructing from binary markers. So smoothing becomes a width-tuning knob, not a binary→continuous fix. Spec updated (`docs/specs/latch_timeseries_features.md` §5.4). Re-probe encodability once re-analysed.
- **Head WIDTH settled — keep dim 256 (2026-05-27, `run-dim-ablation.sh` + `latch_shape_bench.py`).** 30-epoch width sweep on the onset-density head (batch 64, shared 5% holdout): **dim 256 BEST (val_median 0.160)**, monotonically WORSE wider (512: 0.183, 768: 0.209, 1024: 0.229). Bigger heads have higher *train* loss too → they under-optimize at LR 3e-4/30ep (not overfit); the smoothed-onset-density task doesn't need >4.9M params (dim256 train 0.17≈val 0.16). **A 10-epoch snapshot had falsely shown 512>256 — premature convergence; the small head overtakes by ep30.** `train_latch.py` now has `--dim/--depth/--num-heads`. Throughput grid (`--grid`): items/s rises to batch ~64 at EVERY width (my `B*∝1/dim²` "small-batch-for-wide-heads" guess was WRONG); wide heads OOM past batch ~64–128, so 64 is the practical max regardless. **Verdict: dim 256 / batch 64 (current default) is right; don't scale.** Caveat: a wide head *might* compete with lower-LR+warmup, but no evidence the task needs it. Control-efficacy (vs val_median proxy) still unverified by ear.
- **Optimizer/LR/scheduler matrix (2026-05-27, `run-optim-matrix.sh`/`run-optim-extra.sh`, onset-density dim256 batch64 shared-holdout).** All within ~5% — top: **schedule-free 3e-4 @60ep 0.1461** (needs the long run; @30ep only 0.183 — its averaging wants more steps; LR-sensitive, 1e-3→0.24) ≈ **Prodigy LR-free @30ep 0.1486** (best value: no LR, no schedule, single run) ≈ AdamW 3e-4 @30ep 0.1534 (current default). **Cosine/60ep does NOT help** good configs (AdamW 3e-4 cosine→0.190, worse) — only rescues a too-high LR (1e-3 const 0.219→cosine 0.186). **8-bit Adam (bnb) costs accuracy** (0.179 vs 0.153) — skip (pointless at 5M params). **Lion is U-shaped + very LR-sensitive — sweet spot exactly 1e-5: 1e-4→0.214, 3e-5→0.174, 1e-5→0.146 (TIES schedule-free@60 for best, at 30ep/~13min), 3e-6→0.177.** So top recommendations: Lion 1e-5, AdamW 3e-4, or Prodigy. **Energy (WandB system.gpu.0.powerWatts):** AdamW 3e-4 best quality-per-joule (0.153 @ ~50 Wh); beating it costs disproportionate energy (Prodigy +24% Wh, schedule-free@60 +78%); Lion 1e-5 (cap-adjusted ~50-55 Wh) is the efficiency frontier. dim256 heads draw 210-250W (under the user's 250W cap); only big dims would bind it; startup boost+tuning spikes to ~310W then settles. **Full stats archived in git-tracked `LATCH_RESULTS.txt`.** WandB API works from here (`api.runs("kim-ake/latch")`) — power/util/temp/loss series all queryable.
- **SEED VARIANCE SUPERSEDES THE OPTIMIZER RANKING (2026-05-28).** 3-seed runs (now that `--seed` exists; same seed → bit-identical, verified): AdamW3e4 0.198±0.031, Lion1e5 0.189±0.030, Prodigy 0.193±0.032 — **means within 0.01, std ~0.031 → statistically INDISTINGUISHABLE.** Variance is REAL (same ~0.031 std under best/last-5-mean/final metrics — not a best-of-epochs artifact); seed 0's init was unlucky for ALL three. **So the entire fine optimizer/LR leaderboard (Lion 1e-5 "best 0.146", etc.) was SEED LUCK from unseeded single runs.** Honest conclusion: optimizer choice doesn't matter for quality → **use AdamW 3e-4** (cheapest/fastest/lowest-energy); fine-LR/optimizer tuning here is below the noise floor — don't chase it. The real lever is VARIANCE REDUCTION via MORE DATA — **CONFIRMED (2026-05-28): doubling data 0.3→0.6 cut std 3.7× (0.032→0.009) AND improved quality 15% (mean 0.194→0.165); the "unlucky" seed 0 went 0.239→0.153.** So the big seed-variance was a SMALL-DATA ARTIFACT — the 30% subset (chosen for fast iteration) cost ~15% quality + ~4× variance. **SESSION PUNCHLINE: the bottleneck was DATA QUANTITY, not optimizer/LR/architecture/smoothing. Train production heads on ≥60% (ideally full) data; reserve 30% subset for coarse screening only.** Only COARSE tiers (good ~0.15 vs bad-LR ~0.21) are real. **METHOD LESSON: never rank LatCH configs from single unseeded runs — std≈0.03 swamps sub-0.03 differences; use `--seed` + multi-seed error bars.** Power-cap study: 308→250W = -19% energy/+1.6% time (near-free, but ONLY because dim256 is overhead-bound; compute-bound loads bind the cap). `train_latch.py` now has `--optimizer {adamw,lion,prodigy,adam8bit,schedulefree}` + `--scheduler {none,cosine}` + `--save-best-only`; schedule-free needs `.train()/.eval()` toggling (handled: eval+save use averaged weights). Installed lion-pytorch/prodigyopt/schedulefree/bitsandbytes(0.49.2, works on AMD) in venv. **Recommendation: Prodigy as set-and-forget default, or keep AdamW 3e-4; schedule-free@60 for max. Spread is small → ear/closed-loop should decide.** NOTE: a first overnight matrix was contaminated by a mid-run system sleep (GPU state corrupted → cosine runs read ~0.21-0.24 garbage); reran clean. **LESSON: don't trust training runs that spanned suspend/resume.**
- **Standardized retrains CONFIRMED (2026-05-26, 30 ep):** `spectral_flatness` val_median 0.099 (recovery holds at full length), `spectral_skewness` 0.118 (still falling at ep30 → more epochs help). **`hpcp` head DONE (2026-05-27, 30 ep, `latch_train_hpcp.yaml` subset 0.3 / 16 workers / preload):** converged cleanly, **val cosine-distance 0.055 → ~0.945 cosine similarity** on held-out chroma — a strong harmony head at `latch_weights/latch_hpcp_v2_best.pt`. Trained ~39 it/s (subset fix worked). NOTE val is the 2% in-subset split (no holdout_frac), not the density sweep's full-pop holdout — don't cross-compare absolutes. **To USE it, need a 12-D chroma TARGET-VECTOR builder** (key/chord → 12-vec) in inference/UI — the scalar slider can't express a chroma profile (test-inference is off for hpcp for this reason). That builder is the remaining work to make hpcp a wieldable control.
- **CORRECTION (2026-05-26): the "dead" heads are NOT fundamentally dead.** The linear encodability probe shows the latent strongly encodes almost everything: `spectral_flatness` R²=**0.87**, plus all `hpcp_*`/`tiv_*` (harmony), bpm/beat_count/syncopation (rhythm), lufs/warmth/sharpness/brightness, etc. R²>0.5. Only `tonic`/`tonic_strength`/`atonality`/`reverberation` are moderate (~0.3).
- So `spectral_flatness`/`tonic_strength` heads are **collapsed-to-mean (a TRAINING failure)**, not signal-absent — confirmed: insensitive even at t=0 clean, yet probe R² high. **Pattern: low-variance features (std≈0.12) collapse under uniform-t noising; high-variance ones learn.**
- **CONFIRMED fix (2026-05-26): target standardization.** `--standardize` (train+guide in zero-mean/unit-std space, un-standardized at inference) recovered flatness: sensitivity **0.10 → 0.42 (WEAK→OK)**. Root cause was small output scale → negligible guidance gradient, not missing signal. Bonus: standardizing ALL regression heads makes the guidance scale uniform across features (same ρ/μ/weight everywhere). **Recommend standardize-by-default for regression heads.**
- Lesson: **probe encodability (cheap, linear) BEFORE concluding a feature is uncontrollable** — a collapsed head ≠ unencodable feature. The probe also greenlights the native-conditioner fine-tune (almost all features encoded). See `scripts/MODELS_ROADMAP.md`, [[latch-verification]].
- **`tonic_strength` / `tonic` — SKIP (empirically input-insensitive).** The head predicts ≈the dataset mean for every clip (pred_std≈0.05) and its ‖∂pred/∂z‖ is ~100× lower than the rms heads (0.015 vs ~1.5) — the feature is low-variance / weakly encoded in the latent, so guidance has ~nothing to push. Not a training bug; more epochs won't help. These are weak-payoff controls; prefer `hpcp` for harmony.
- **Screen any new head with `scripts/latch_head_sensitivity.py`** before wiring its slider: tiny `pred_std`/sensitivity ⇒ dead-for-guidance regardless of gain/weight.
- UI: ρ/μ sliders → 30, Weight → 50 (Weight multiplies the gradient — the real strength knob). Clamped (rms) heads slider = full clamp range [−60,0] for over-drive.
