# TRAINING — standing directives, general findings, required logging

**Read this before launching or interpreting any training run** (SA3/SAME LoRA/DoRA/full-FT, LatCH heads, control adapters, optimizer or LR brackets).

*Built 2026-10-07 by THE-FINN at WINTERMUTE's request (Kim: "a directive pointing to a training.md where we record directives and general findings"). It is an INDEX of rules and cross-run findings, each with a pointer to the evidence. It does not repeat the dated log: **`docs/training-findings.md` is the chronological log** (postmortems, A/B/C failure catalogue) that this file cites. Operator manual for the modular trainer: `docs/train_lora_modular.md`. Facts that silently give wrong results (EMA, GPU lock, venvs): `.claude/skills/sa3-training/SKILL.md`. Experiment registry: `EXPERIMENTS.md`.*

**How to use it.** §1 = rules (do / don't), each with a one-line why. §2 = what holds across runs, with confidence. §3 = what a run must record. §4 = open items and known discrepancies. When a rule here and a source disagree, the SOURCE wins and this file is wrong: fix it (owner: THE-FINN with the training owner; see `OWNERSHIP.md`).

**Confidence key.** **High** = mechanism understood or measured with a margin well above the noise floor. **Medium** = measured, but one run, one seed, or a reading that rests on a single comparison. **Weak** = single seed inside the noise floor, an ear verdict not yet backed by a measurement, or secondhand. **Prelim** = Kim's ear, not yet audited.

### 2e. Optimizer mechanics: what cancels, what averages out, what rounds away (KUANG, 2026-10-17)

*Plain-language primer first, because the rows below assume it.*
- **Gradient noise.** Each batch gives a gradient = the true direction + noise. With batch 1-16 (our FiLM, LatCH and DoRA runs) the noise is large compared with the signal. Momentum (averaging gradients over the last ~10-20 steps) is what removes most of it; anything that looks at the *difference* between two consecutive gradients, or at a per-element signal-to-noise ratio, mostly sees noise.
- **Update size.** How far each weight moves per step. Our Muon-family optimizers fix this size by construction (Newton-Schulz makes the update "unit size", NorMuon equalises rows), so the learning rate and a few scale rules decide it, not the gradient. Any multiplier applied BEFORE Newton-Schulz/NorMuon is undone by them.
- **Precision.** bf16 keeps only 2-3 significant digits: a weight of 0.03 can only take values about 0.0001 apart, so a step smaller than about half of that (0.2-0.4% of the weight) is rounded to nothing. Schedule-Free's averaged weights move by (2/step number) of the gap each step, so after a few hundred steps their changes are tiny and bf16 drops them.
- **The general rule:** a mechanism can be (a) cancelled by a later stage, (b) averaged away, or (c) rounded away. Each looks like "no effect" or, worse, like a different effect.

## 3. REQUIRED LOGGING — per run

**Why this section exists (the gap).** MASTER §4 (2026-06-24) already makes full tiered telemetry a STANDING REQUIREMENT for control-head runs ("you can't backfill"). It was not applied: **LatCH Phase D (16 arms) kept only a 94-line `train.log` per arm (per-epoch train/val) and the epoch checkpoints.** `latch/train_latch.py` has a `--wandb` flag (default off) and `run_modular_bracket.sh` does not pass it, so there is no per-step loss, grad norm, LR or trajectory for any arm, and the checkpoints (per W) store `val_loss` but not lr/schedule. The Phase D trajectory question (does b32 differ at equal steps? when does dim 512 pull ahead?) then had to be answered from 10 numbers per arm.

**Rule: every run, local or LUMI, any trainer, records the following. Nothing here is optional because the run is "just a bracket".**

## 4. OPEN ITEMS and KNOWN DISCREPANCIES between sources

**Discrepancies (sources disagree or leave a gap; each wants an owner decision):**
1. **Path-efficiency as a health meter.** The skill (§7) gives "DoRA-runaway family 0.14-0.23 vs healthy ~0.75-0.78", but training-findings item 21 records the run that "genuinely converges" (attempt 4) with path efficiency **0.216**, inside the runaway band, and goa3 (healthy) at 0.81. Path efficiency alone does not separate the two; `global_norm` (99-114 vs 4085-12189) and velocity do. Prefer global_norm/velocity, and treat path-efficiency as run-family-specific.
2. **"Don't scale head dim past 256" vs Phase D.** `LATCH_RESULTS.txt` §3 ("wider is monotonically WORSE", at b64/30 ep) and §22 vs Phase D dim 512 = 0.1908 (best of 16, single seed, 10 ep, different batch). Different conditions (batch, optimizer, epochs); Phase E E02/E03 (dim 512, 20 ep, repeat seed) is the arbiter. Until then: no default change.
3. **"Smaller batch wins monotonically (b16 > b32 > b64 > b128)"** (training-findings "LatCH head recipe", skill §4 "b16 > b32") came from a **fixed-epoch** sweep (10 ep / 50% subset, 2026-05-30), the same design that produced the Phase D step-count artefact. I could not verify whether that sweep matched steps; treat "b16 > b32" as **unverified** until re-run at equal steps. C already corrected the Phase D readings in E5, KIM-TASKLIST, training-findings and the skill; this older line looks like it is not yet marked.
4. **LR scales** appear contradictory only if read without their optimizer/net: FusionOpt full-FT ≈ 5e-6, ModularOptimizer DoRA 5e-4, ModularOptimizer LatCH head 6e-3..1e-2, LatCH AdamW-equiv 3e-4. Not a conflict; D4 says never copy across.
5. **Unverified-runs list.** Runs that used `--modular-ev`, `--var-dampening`, `--var-barrier-weight` or `--modular-schedule-free` before the 2026-09-21/22 fixes (flags dynamically inert; SF iterate-swap skipped ModularOptimizer) are unverified for those mechanisms (memory note `sao-modular-trainer-flags-unverified`, 2026-09-22). training-findings B9/B10 record the SF-swap fix and the live mechanism audit; I did not find a record that the EV/VADD conclusions were re-run. Check `git log` and `EXPERIMENTS.md` before citing one as evidence.
6. **`--modular-magnitude-update multiplicative`** (F12) was "retry pending" in the 2026-09-24 write-up; whether the retry ran is not recorded in what I read.
7. **"Whitening: never run on audio"** (`docs/train_lora_modular.md` §5c) is true only for the DoRA trainer (default `none`). The LatCH and FiLM trainers default to `--mod-whitening shampoo` and ran it in every modular run (F25). That doc line wants a qualifier.
