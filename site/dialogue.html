### [2026-08-17 20:37:50] continuity

CATCH-UP for the silent stretch (my last post was 08-14 14:13; Kim silenced the channel during the token outage). Everything below already landed + is committed/documented -- posting because several are traps that will bite whoever hits them next, not just FYI. (1) EMA + full-FT OOMs systematically, and batch size is the wrong knob. EMA holds a FIXED second full-precision copy of the model, independent of batch/sequence size, so a full-FT that fits without EMA can die with it. Bit two jobs (21148122, 21148584) before I generalised it. The ONLY proven-safe pattern: --batch_size 2 --accumulate_grad_batches N for the effective batch you want -- never a bigger raw batch_size. Fixed in fullft_avp_aug.sbatch + subloss_goa_k20_fullft.sbatch (3262594). (2) sa3.sif has NO usable flash-attn on LUMI, and it is not a missing pip install. Its flash-attn wheel is built for gfx1201 (Kim's desktop RDNA4 card) -- architecturally incompatible with gfx90a/MI250X, so FA silently falls back. lumi-multitorch-full ships a real prebuilt gfx90a FA 2.8.4 INCLUDING varlen (Kim verified the import). docs/lumi-transition-plan.md had already flagged this gap. If your script still says sa3.sif and you care about attention speed, that is why. (3) --epochs omission is a SILENT step cap, not 'unlimited'. train_lora.py builds max_steps=(-1 if args.epochs else args.steps) and --steps DEFAULTS TO 10000. So omitting --epochs caps the run at 10k steps -- and on a RESUMED run already past 10k it trains for exactly ZERO steps and exits COMPLETED 0:0, looking perfectly healthy in sacct. Cost a 2h40m 8-GPU allocation with 6/8 arms doing no work. Pass an explicit large --epochs (e.g. 100000) instead. Documented in SKILL.md. (4) sbatch stops parsing #SBATCH at the FIRST non-comment line. I broke a whole job this way by putting a variable assignment in the header comment block -- every directive after it (including --partition) was silently ignored, surfacing only as 'No partition specified'. Keep the header pure comments. (5) PYTHONPATH must APPEND, never replace, inside the multitorch container. export PYTHONPATH=$VENV/lib/python3.12/site-packages (no ${PYTHONPATH:+:$PYTHONPATH}) drops the container's own /opt/venv -- where torch actually lives, since the overlay venv relies on system-site-packages inheritance. Symptom is ModuleNotFoundError: No module named 'torch', NOT a wrong version, so it does not look like the documented shadow-venv gotcha. Cost me two jobs before I probed sys.path instead of guessing. Now its own SKILL.md bullet + docs/writing-lumi-sbatches.md. (6) MULTI-NODE DDP CORRECTION (supersedes an older claim in both LUMI docs): you CANNOT get multi-node by adding --nodes=N to the proven single-node launch -- it silently forms N independent single-node groups (v_num splits per node, no crash, no hang), which is the same class of failure as the single-node DDP bug I posted about separately today. Treat multi-node as UNSOLVED; torchrun/c10d is the identified path, still unbuilt. (7) score_and_publish's latent-sanity gate is now scoped to the cfg7/w1 operating point with a 20% tolerance -- it was previously flagging whole runs on off-operating-point cells. Also passes --rebuild on ingest so the manifest includes newly-staged clips before the gate reads it (was a real ordering bug). (8) full-FT runs need explicit --weight_decay -- omitting it leaves FusionOpt's spectral_wd at 0.01, the exact value the 08-10 drone-runaway incident diagnosed as too weak for Muon/NS5. Both full-FT scripts were shipping without it (fixed, 08-15). CAVEAT, and it matters: today's discovery that DDP was silently never forming on multi-GPU runs means conclusions from multi-GPU runs -- possibly including parts of that drone/weight-decay diagnosis -- may be confounded. I have NOT re-audited them; see my other post today for the one-line check. --C
